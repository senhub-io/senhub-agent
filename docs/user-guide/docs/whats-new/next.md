# Next (unreleased)

Nothing released yet since 0.7.1. Changes land here as they are merged.

- **Linux: no absurd network rate after an interface reset.** When an interface counter went backwards (interface reset, driver reloaded, a 32-bit counter wrapping), the network probe published a rate of about 10^19 for that cycle. It now skips the rates of that interface for that cycle and starts again from the new value.

- **PRTG and Nagios no longer wait on a probe that could not start.** In the minutes after the agent starts, a reading of a probe that has no data yet waits up to 10 seconds for its first collection. A probe that failed to start, a Pro probe without a licence for example, will never collect, yet each of its readings waited the full 10 seconds. It now answers at once, as for a name the agent does not know.

- **Services carry their run state in the topology.** The `host.service` entity of a systemd unit or a Windows service now has a `status` attribute: `running`, `stopped`, `starting`, `stopping`, `paused`, `failed` (systemd only) or `unknown`, never left out. On Linux, an enabled unit that systemd has not loaded is listed too, as `stopped`, so a stopped automatic-start service shows in the graph instead of being absent. The `host.service.running` series is unchanged and stays the one to alert on.

- **SNMP device vendor: one attribute, from the enterprise number.** A polled device carried both `vendor` (from its enterprise number) and `hw.vendor` (from the chassis ENTITY-MIB name, such as `Cisco`). It now carries `hw.vendor` only, the short lowercase name of its enterprise number (`cisco`, `juniper`, `fortinet`, ...), with the ENTITY-MIB name used only when the number is not known, and `senhub.hw.vendor.source` says which (`iana_pen` or `entity_mib`). Fortinet devices are now named. A topology query on `vendor` should read `hw.vendor`.
- **ICMP checks: no observer attribute on the address.** The `network.address` an `icmp_check` probe reports no longer carries `senhub.check.probe_host.id`. The address is shared by every agent that pings it, so the attribute changed with each report; the observer is the `monitors` relation from the agent.

- **Before you upgrade: on Linux, CPU usage now covers the whole probe interval.** `cpu_usage_total` and `cpu_core_usage` (the PRTG "CPU usage total" and per-core channels, `system.cpu.utilization` in OTLP) were the usage of the single second before each collection, and each collection paused two seconds to measure it. They are now the average over the probe interval, from the same counters as the per-mode shares, so the values are smoother: a short burst no longer shows as a peak, and an idle second no longer hides a busy minute. They appear from the second collection after a start. Thresholds set on the old one-second values may need a look.

- **Linux: an optional eBPF helper names the processes behind other users' connections.** The packages now ship `senhub-ebpf` and its systemd unit, disabled by default. Once enabled (`systemctl enable --now senhub-ebpf`, kernel 5.8 or newer with BTF), the dependency map attributes sockets the unprivileged agent cannot read, and `senhub.connection.retransmits` follows the kernel's per-socket count. The agent keeps its profile; the helper runs apart, with only `CAP_BPF` and `CAP_PERFMON`. `senhub-agent doctor` reports its state, and `entities.ebpf.enabled` (default `true`) switches the agent's use of it. Without the helper nothing changes. See [eBPF connection owners](../ebpf.md).

- **OpAMP (Enterprise): adopt a local probe and receive sealed secrets.** A fleet server can now take over a probe defined in the local file: the server's definition runs under the same name and the local copy stays inert until the overlay is withdrawn. The agent announces `io.senhub.adopt/v1` and reports its local probes (masked) so the server can offer them. The server can also deliver secrets to managed probes without ever sending them in clear: the agent creates its own key pair, keeps it in its secret store, and managed probes refer to the values as `${secret:fleet.<name>}`. The key pair rotates every 90 days, on the server's request, or with `senhub-agent opamp rotate-keys`, with no gap in service; `senhub-agent opamp key` prints the key id and fingerprint to compare with the server. New refusal codes: `adopt_target_missing`, `adopt_type_mismatch`, `adopt_env_defined`, `adopt_retarget_with_local_secret`. See [OpAMP remote management](../opamp.md).

- **OpAMP (Enterprise): the server can drive the update.** A fleet server can turn the automatic update on or off and give the version to run, with a downgrade only when it says so. For this block the signed overlay wins over the `auto_update` file; withdrawing it gives the file back at once. The versions allowed come from the signed registry list, checked against the key built into the agent. The agent reports `senhub.update.state`, `senhub.update.target`, `senhub.update.reason` and `senhub.install.kind`. See [OpAMP remote management](../opamp.md#updates-driven-by-the-server-v2).

- **`.deb` and `.rpm`: a root unit installs the version the service asks for.** The packages now ship `senhub-agent-update.path` and `.service`, enabled at install. The unprivileged service writes the wanted version to a request file; the root unit refuses anything but a plain version, a file not owned by the service user, writable by others or a symbolic link, checks the signed version list, the archive signature and the key built into the agent, replaces the binary, and restarts the service. A failed start returns to the previous version through the same unit. This is how a fleet server updates a package install. Disable it with `systemctl disable --now senhub-agent-update.path`; such an install then answers `not_replaceable`. See [the root update unit](../installation.md#the-root-update-unit).

- **`.deb` and `.rpm`: the root update unit no longer stops after a few refusals, and the agent reports why.** The unit had a systemd start limit that, once reached, left its path unit failed until an operator ran `systemctl reset-failed`: no later update was handled. The limit now lives in the update command (six attempts an hour, then the reason `rate_limited`, recovering by itself), and the unit reports each outcome to the agent, so a server sees `senhub.update.state=failed` with the reason. The service unit also sets the directory modes the packages create (0750), which removes the `ConfigurationDirectory ... mode is different` warning at each start.

- **Windows MSI: a new install updates itself.** The installer wrote `auto_update.enabled: false`, so an agent installed from the MSI stayed on its first version, although the MSI path is built to apply each new signed MSI. A new install now turns automatic updates on. Pass `AUTO_UPDATE=0` to `msiexec` when Intune, SCCM or another tool manages the version. An existing configuration is not changed: an agent installed before keeps its setting; to turn updates on there, set `enabled: true` under `auto_update` in `%ProgramData%\SenHub\agent.yaml`.
- **The update setting can be read from outside.** Two self-metrics say what the updater does on each agent: `senhub.agent.update.info` (`enabled`, `include_beta`, `target`, and `source`: the local file or a server directive) and `senhub.agent.update.paused`. `senhub-agent status` prints the same line, and `status --json` carries it under `agent.update`; before, the setting could only be read with `config show` on the host, and a pause set by a fleet server was visible only in the log. A fleet server also receives `senhub.update.self_replace`, which says whether the agent can install a new version by itself, so it can refuse a target before sending it rather than when the agent applies it.
- **Docker Swarm: no failing default probe when the agent cannot open the Docker socket.** The install wrote `probes.d/06-swarm.yaml` as soon as `/var/run/docker.sock` existed, and on a host where the `senhub` user is not in the `docker` group the probe failed every cycle while `doctor` reported it OK. The default fragment is now written as `06-swarm.yaml.disabled`, with the reason and the fix at the top, when the service user cannot open the socket. A Swarm probe that cannot reach the socket now reports its cycle as failed, so `status` and `doctor` show the error; its `senhub.swarm.up = 0` series is still sent.
- **ping_webapp: the error says how to allow ICMP under the packaged service.** On Linux, a `ping` refused by the packaged unit now ends its error with the two fixes, a `CAP_NET_RAW` drop-in or `net.ipv4.ping_group_range`, which the [ping_webapp page](../probes/ping-webapp.md) details. The unit itself is unchanged: no capability is granted by default.
- **Windows: the service comes back after a failed update, and `install` can be run again.** The service manager restarted the agent only after a crash: an agent that stopped cleanly with an error, which is how it exits after rolling a failed update back, stayed stopped. The service now restarts on every failure, a clean exit with an error included, 10 seconds later, and the agent sets this itself at start on services installed by an earlier version or by the MSI. Running `senhub-agent install` again on a machine where the service is already registered no longer fails with `service senhub-agent already exists`: the registration is brought back to this install (command line, automatic start, recovery), nothing is restarted, and a service installed by the MSI keeps its command line.
- **The release signing key has a stable address.** The minisign public key that signs every download, and that the agent embeds, is published at `https://packages.senhub.io/releases/minisign.pub` beside the release manifests, which name it in a new `signing_key_url` field. Before, it could only be copied from the documentation.
- **The redacted configuration shows the OTLP tenant header again.** Since 0.7.1 every OTLP header value was masked in `config show --redact`, in the console and in the configuration sent to a fleet server. `X-Scope-OrgID` is now shown, so the tenant can be read; `Authorization`, `Cookie`, `X-Session` and every other header stay `***`.
- **`config check` reports keys of the `agent:` block that do nothing.** A key the agent does not read inside `agent:` was dropped without a word: a misspelt `licence:`, or settings of older versions such as `update_check_interval`, `mode` or `generated`. `config check` now names each one in a warning (exit code 1), as it already did for top-level and probe keys. Remove them from `agent.yaml`; nothing else changes, the update check still runs every hour, at start and on every configuration change.

- **Events sent to the SenHub cloud are no longer duplicated when an answer is lost.** When the intake stored a batch of events but its answer was lost or late, the agent re-sent the whole batch, up to twelve times in one cycle, and every copy was stored again. Each event now carries a `senhub_event_id` set once when it is queued and kept on every resend, so the intake can recognise a copy, and the batch is posted once per attempt. The first resend of a failed batch now waits five to seven seconds, so the intake can already see the events it stored: the only retries left are the agent's own, and `senhub.export.send_failed` counts one failure per cycle that ends without delivery, as for the other outputs.
- **Events survive an intake outage of several hours.** Events the SenHub intake does not acknowledge are now kept on disk (`event-queue` under the agent state directory), replayed in order when it answers again, and deleted only once acknowledged, so a restart during the outage loses nothing. The backlog is capped at 128 MiB and 24 hours (`backlog_max_bytes`, `backlog_max_age`, `backlog_path` on the `event` storage), the oldest events going first and being counted. Stopping the agent while the intake is down no longer waits up to two minutes: the final flush ends at the shutdown deadline and leaves the rest on disk.
- **Learned neighbours no longer come and go on every read.** A switch forgets an idle MAC address within minutes, and the agent deleted the neighbour each time, then created it again at the next read: on a large network, thousands of false changes an hour in the topology. A `network.neighbor`, read over SNMP or from the host's ARP table, is no longer deleted when a read stops listing it. It announces a liveness interval of 24 hours and the topology retires it when no read has listed it for that long, so a neighbour that really left stays visible for up to a day. Above `max_neighbors`, a neighbour already published keeps its place against the others of its kind (resolved, with an address, or neither) while it is listed, instead of changing with every arrival.

- **`senhub.neighbors.omitted` is replaced by `senhub.neighbors.truncated`.** The number of neighbours cut by `max_neighbors` changed at almost every read on a cut device, and each change was recorded in the topology. The device entity now carries `senhub.neighbors.truncated`, a boolean that changes only when the cut starts or stops; `senhub.neighbors.limit` is unchanged, and the exact count stays in the agent log line `neighbor table bound: some neighbors omitted`.

- **The OTLP checkpoint is saved again when a metric is not a number.** One NaN or infinite value in the metrics kept for the OTLP output made every checkpoint save fail (`OTLP checkpoint save failed: json: unsupported value: NaN`), so a restart restored old values or none. Such values are now left out of the checkpoint, and the agent logs the metric name once.

- **The network probe reports host TCP counters.** Connections by state, connections opened, failed and reset, retransmitted segments, resets sent and, on Linux, listen queue overflows, for the whole host. They are on by default; `tcp_stats: false` leaves only the per-interface metrics. On Linux the connection counts come from the kernel socket table and need no extra privilege; on Windows the counters come from the IP Helper API, without listen overflows.

- **The configuration views mask more of what may be a secret.** `config show --redact`, the console and the configuration an agent reports to its fleet server now also mask a value taken from `${env:}`, the path of a webhook URL (Slack, Teams, Discord, Google Chat, Logic Apps, and self-hosted hooks) and any value that looks like a token, a known prefix or an opaque high-entropy string, whatever its key is called. Before, a secret under a key with a harmless name, or in a webhook URL, was shown in clear.

- **Outbound dependencies report their connection quality.** On Linux, for each dependency the agent publishes, the network probe now reports the mean round-trip time (`senhub.connection.rtt`), the segments retransmitted (`senhub.connection.retransmits`) and the bytes exchanged in each direction (`senhub.connection.io`). The series carry the keys of the dependency (service, server address and port, transport, and the host for a local target) and never the client port, so a connection coming and going does not create a series. The counters keep growing for as long as the dependency exists. They follow `tcp_stats`; a dependency excluded by `depends_on_exclude_cidrs` has none.

- **Inbound callers of local listeners, in the logs.** With `entities.inbound_callers.enabled` (off by default, needs an OTLP output that sends logs), the agent reports which addresses connect to each listener of the host as log records `senhub.listener.caller.seen`, `.gone` and a 15-minute `.activity`, and as the metric `senhub.listener.caller.count`. Callers are never sent to the topology. Public addresses are reported in clear by default; `inbound_callers.public_addresses` keeps only their /24 or /48, or only counts them. See [Configuration](configuration.md#entities-section).

- **Metrics and traces survive a collector outage.** A push or a span export the collector did not take is now kept on disk, as the request the agent built with its own timestamps, and sent again in order when the collector answers, also after an agent restart: the history of a 4-hour outage reaches the collector instead of only the last value. A file is deleted only after the collector acknowledged it. The queues live next to the logs queue in `otlp-queue/` of the state directory, are on by default, and are bounded to 256 MiB for metrics and 64 MiB for traces, 24 hours each (`metrics_queue_max_bytes`, `metrics_queue_max_age`, `traces_queue_max_bytes`, `traces_queue_max_age`; `SENHUB_METRIC_QUEUE*` and `SENHUB_TRACE_QUEUE*`). What a cap or the age limit drops is counted in `senhub.agent.otlp.dropped` as `metrics_queue_full`, `metrics_dropped_by_age`, `traces_queue_full` or `traces_dropped_by_age`. See [Logs, metrics and traces survive an outage](../otlp.md#logs-metrics-and-traces-survive-an-outage). An overloaded collector is no longer hammered: the agent honours `Retry-After` (HTTP 429 and 503) and `RetryInfo` (gRPC) for logs, metrics and traces, waits at least that long, up to 10 minutes, keeps new data on disk meanwhile, and counts it in `senhub.agent.otlp.throttled` instead of the export errors. Logs relayed from an OTLP receiver are kept on disk in a queue of their own when the collector does not take them, instead of being dropped. The replay clock now tops out at 60 seconds instead of 5 minutes, and a live export that succeeds while a backlog waits starts the replay at once, so a returning collector gets the history before a capped queue evicts it. Traces now follow `fallback_endpoints` like metrics and logs, and so do the relays. A queue that evicts under its size cap logs one warning per minute with the totals instead of one per batch.

- **`senhub.routes.omitted` is replaced by `senhub.routes.truncated` on SNMP devices.** Same change as for neighbours: the number of routes cut by `max_routes` moved with the routing table and each move was recorded in the topology. The device entity now carries `senhub.routes.truncated`, a boolean that changes only when the cut starts or stops; `senhub.routes.limit` and `senhub.routes.filtered` are unchanged, and the exact count stays in the agent log line `route table bound: some routes omitted`. Host entities keep `senhub.routes.omitted`.

- **An SNMP interface that disappears for one sweep is now deleted reliably.** When `interval` and `topology_interval` were equal, the poll cycle that fell one interval after a sweep started a few milliseconds early and skipped it, so the real sweep period was often twice the configured one and a short absence could fall between two sweeps without ever being deleted. The cycle now sweeps when it is within a tenth of `interval` of the topology interval. Each stored sweep is logged at debug level (`topology sweep stored`).

- **`zabbix setup` now imports the template dashboards.** On Zabbix 7.0 and later the command imported the templates but not their dashboards, so the **Dashboards** menu of a host stayed empty although the documentation promised one dashboard per template. Re-run `zabbix setup` against an existing server to add them. The widgets are also headed with the chart name ("CPU utilization") instead of the raw `{#PROBE}: CPU utilization` macro text.

- **`zabbix setup --host` links the templates of a probe added after a host registered.** The autoregistration action only runs when a host first registers, so a probe enabled later on a registered host got no template and no data in Zabbix. `zabbix setup --probe <type> --host <name>` now links, on the hosts you name, the templates of the run that they do not link yet, keeps what they already link, and touches no other host; `--dry-run` shows what it would link.

- **A value read from `${secret:}`, `${env:}` or `${file:}` never appears in the agent log.** The "Configuration changes detected" and "Starting new probe" lines masked only keys recognised by name (`password`, `bearer_token`...): a secret under a neutral key such as `x_ref`, or inside a URL, was written in clear. The agent now masks every value that came from a reference, whatever its key, including in the parameters of managed probes. A value taken from the `:-default` part of a reference is written in the file, not secret, and stays visible.

- **`license show` and `doctor` say who signed the licence.** For a licence issued through a delegating platform, `senhub-agent license show` prints the platform, the delegation key id and the date the delegation ends, and the `config.license` check of `senhub-agent doctor` carries the same information. A licence signed by the root key says so. Renew the licence, or ask the platform to renew its delegation, before the delegation ends.

- **`senhub-agent doctor` warns when the dependency map cannot see other users' connections.** With `entities.depends_on` on, a service account that holds neither `CAP_DAC_READ_SEARCH` nor `CAP_SYS_PTRACE` sees only its own connections, so a host with no dependencies and a host not allowed to see them looked the same. The new `install.depends_on_caps` check reads the unit and its drop-ins. The [OTLP](otlp.md) page now says the service account is enough once a drop-in grants those two capabilities, and that a loopback peer on a service port is kept while one on an ephemeral port is dropped.

- **`filetail` no longer re-reads a whole file on Windows when its size lags.** A writer that keeps the file open with buffered writes can leave the size seen by path behind what the agent has already read. The agent took that for a truncation and, after 30 seconds, read the file again from the first byte, sending its lines a second time. It now treats a shorter size as a truncation only when the first bytes of the file have changed too or the file is emptied; a stale size alone no longer restarts the tail.
- **OTLP exports each measurement once, at the time it was taken.** A push no longer sends every stored series again stamped with the push time: a probe that runs every 60 s under a 30 s push now sends one point per run, and the points show the probe's cadence. A gauge from a probe that runs less often than `keepalive_interval` (4 minutes by default) is exported again at that interval while its probe still vouches for the value, so it stays visible under a 5-minute lookback; counters and histograms are never exported again. Set `keepalive_interval: 0s` to export every measurement once and only once. Dashboards that relied on a point every push for a slow probe should use a lookback of at least `keepalive_interval`. See [What time a point carries](../otlp.md#what-time-a-point-carries).

- **The release manifest lists the `jt400runner` binaries.** `manifest.json` now carries `jt400runner-linux-amd64` and `jt400runner-linux-arm64` with their size and sha256, under the new `kind` value `native`, so a check of the files of a release covers them like the archives and packages. Clients that read only the `zip`, `msi`, `deb` and `rpm` entries are not affected. See [Releases](releases.md).

- **`config check` and `doctor` say when a single-file configuration cannot be split.** An agent whose `agent.yaml` still holds `probes:` or `storage:` splits it into `probes.d/` and `strategies.d/` at start, but refuses when files you wrote already sit in those directories, since the agent ignores them today and the split would start them. That refusal was a log line at each start and nothing else. `config check` now names the files in a warning (exit code 1), which `doctor` shows too; move what they hold into `agent.yaml` or remove them, then run `senhub-agent config migrate`. A single-file configuration with nothing in the way gets an information line saying it is split at the next start.
- **`config check` reads inside the OTLP and Zabbix sub-blocks.** A misspelt key inside the `otlp` output's `tls`, `retry`, `persistence`, `memory_limit`, `relay` or `signals.<signal>` blocks (and a signal's own `tls`), or inside the `zabbix` output's `tls`, `passive` and `passive.tls`, was ignored without a word. `config check` now names it with its full path, for example `signals.logs.tls.ca_fiel`, in a warning (exit code 1). Blocks whose keys you choose, such as `headers` and `resource`, are not checked.
- **Redfish: an error is no longer taken for a missing resource because of its address.** The probe treated any error whose text contained `404` as an absent resource and skipped it silently. The text carries the BMC address, so a BMC reached on a port or path containing `404` hid real 403 and 500 errors. The probe now reads the HTTP status code.
- **Docker: no more debug line per cycle for a container without a memory limit.** `memory.max` and `pids.max` hold `max` on such a container, which the probe logged as an unreadable file at every cycle.
- **Licences: the tier is checked, and a licence can name an agent by its `service.instance.id`.** A licence with no `tier`, or a tier other than `free`, `pro` or `enterprise` (any case), is now refused instead of being taken as a licence of unknown scope. A licence bound to one agent may give that agent's `service.instance.id` as its subject instead of the agent key, so the key no longer has to appear in a licence. The agent also checks `iss`, `aud` and `nbf` when a licence carries them, and selects the signing key by the `kid` header, which prepares a rotation of the signing key. Every licence issued so far stays valid. See [the licence system](https://github.com/senhub-io/senhub-agent/blob/master/docs/LICENSE-SYSTEM.md).
- **A configuration copied from another machine is reported, and `config regenerate-key` gives the copy its own identity.** A server cloned after the agent was installed keeps the agent key, so two agents reported under one `service.instance.id` and nothing said so. The agent now records the host it runs on beside its identity and, at start, logs a warning when the configuration came from another machine; `senhub-agent doctor` fails with `install.identity`. When a fleet server refuses the connection because the same identity is already connected (`instance_uid already connected`), `doctor` fails with `install.identity.fleet`. `senhub-agent config regenerate-key` writes a new agent key after confirmation and lists what to update (service restart, PRTG URLs, a licence bound to the agent, the fleet record). See [config regenerate-key](../cli.md#config-regenerate-key).

- **Enterprise: the fleet server can deliver the licence, and revoke one.** With `opamp.license_from_server: true`, the agent receives its licence from the server, checks it completely (signature, tier, binding to this agent, expiry), writes it to `license.jwt` and applies it without a restart; `license activate` and `license remove` then refuse, so the licence has one writer. The server can also send a signed revocation list: a revoked licence drops the agent to the Free tier at once, without grace, and an older list cannot be sent again to lift a revocation. A site with no outbound flow imports the list with `senhub-agent license revocations import -`. The agent reports `senhub.license.source`, `senhub.license.state` and `senhub.license.revocations.version` to the server. See [OpAMP remote management](../opamp.md#licence-delivered-by-the-server).

- **A new licence takes effect without a restart, and an expired one stops what it allowed.** The agent validated its licence only while it had none, so a renewed licence waited for a restart, a licence that expired while the agent ran stayed in force, and a paid probe kept running after its licence was gone. The licence is now evaluated again at every configuration change and when it passes from valid to grace and from grace to expired, and a running probe the licence no longer allows is stopped.

- **An OpAMP token written in clear is sealed.** At start the agent moves the secrets written in clear in its configuration into the OS secret store, but it left `opamp.token` in `agent.yaml` as typed. It is now sealed with the agent key, under `${secret:opamp.token}`. A token already given as a reference is left alone.

- **Console fixes.** In a browser session, Settings no longer offers to reveal or copy the administration key, which it does not hold and showed as `_`; it says how to get it on the machine. A clean save no longer shows a warning banner. The Overview calls a probe that is not running yet "starting", as the Probes page does. A probe page whose current values cannot be read because the PRTG endpoint is off says so. A disabled output shows one Enable button, and "Add an output" opens the add form.

- **A container keeps one Zabbix host across deployments.** The Zabbix output registers under the machine's host name, and a container platform such as Azure Container Apps gives each replica a new one on every revision: every deployment created a new Zabbix host and the old one went silent. `SENHUB_ZABBIX_HOSTNAME` in the container image, and `config init --zabbix-hostname` elsewhere, now set the name the host registers under. See [the container variables](../container.md).

- **`license activate`, `license remove` and `license revocations import` apply on a running agent.** The agent watched `agent.yaml` but not the `license.jwt` and `license.revocations.jwt` files beside it, so a licence set from the command line, or a file dropped in place, waited for a restart. The agent now watches the directory of `agent.yaml`, limited to that file and the two licence files, and applies a change within a few seconds. Other files in that directory still trigger nothing.

- **`senhub.agent.license.expires_in`.** A new self-metric gives the seconds until the licence in force expires, negative during the grace period, with `state` (`valid` or `grace`) and `platform` (the delegating platform, empty for a licence signed by Sensor Factory). An agent in its grace period can now be alerted on instead of being found in one log line.

- **`license activate` on Windows no longer fails with `Access is denied` while the service runs.** It rewrote `agent.yaml` to clear an inline licence even when there was none, and the running service held the file. `agent.yaml` is now left alone when it carries no inline licence.
